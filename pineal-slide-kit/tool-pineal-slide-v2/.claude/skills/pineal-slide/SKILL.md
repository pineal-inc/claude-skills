# pineal-slide

通常の新規作成は **HTMLを編集用の正本とし、ブラウザで閲覧・発表、必要に応じてPDFを出す**。
リポジトリ名は `tool-pineal-slide-v2` のままだが、既定のテンプレートは `templates/html/` に更新されている。
ユーザーはAIへの指示で直す運用を想定している。

## 使う方式

- **新規作成・HTMLテンプレートへの移植**: このページと [HTMLキットのREADME](../../../templates/html/README.md) を使う。
- **既存資料の修正**: 対象のHTML・CSS・素材を確認し、その資料の方式を保って修正する。移行の依頼があればHTMLキットへ移す。
- **編集可能なPPTXも必要**: HTML版を内容の正本にしたまま、pineal-slide-v3 のテンプレ（`pineal_temp.pptx`）の型を1枚ずつ起こし、[pptx/pptxlib.py](pptx/pptxlib.py) の部品でボディを組む。手順（設計書 → パイロット8枚で承認 → 残り → 結合 → PowerPoint描画で全ページ目視 → 直下配置と旧版の `archive/` 移動）は [PPTX出力の手順](references/pptx-v3.md)。文体と構成の判断はこのページのまま。依頼されていないPPTXは生成しない。
  - 現HTMLキットは旧 `html2pptx` の互換サブセットではない。HTMLからの直接変換を約束しない。
  - 社内情報入りの型（Board Member・Media・Client・お問い合わせ）はパートナー・顧客向け資料に使わない。

## 内容を組む

目的、受け手、伝えたい結論、元資料、枚数の目安を会話と資料から把握し、足りない情報だけを聞く。
既に合意した内容や、指摘箇所の修正を始めるために確認を繰り返さない。
新規構成では各ページの結論を並べて、主張がつながるか確かめる。必要に応じてユーザーと構成を調整する。

元資料がある場合は文章だけでなく、画像・図・画面と説明の関係を確認する。
意味を担う図を理由なく落としたり、カードの羅列に置き換えたりしない。
商務条件、数値、固有名詞、引用は元資料に照合し、変更指示なしに更新しない。

## テンプレートを使う

まず [HTMLキットのREADME](../../../templates/html/README.md) と、必要な作例の実際のHTML/CSSを読む。
シンボリックリンク経由の場合は、このスキルの実体ディレクトリを解決する。
実体の3階層上がリポジトリのルートで、そこに `templates/html/` と `scripts/create-html-deck.mjs` がある。

- `templates/html/gallery/pages.html`: 基本構成、部品を混ぜた例、自由設計の例
- `templates/html/gallery/blocks.html`: 部品カタログ

リポジトリ直下で、独立して開ける資料フォルダを作る。

```bash
npm run deck:new -- /保存先プロジェクト/slides/資料名
```

または `node /リポジトリの絶対パス/scripts/create-html-deck.mjs /保存先` を実行する。
既存フォルダには上書きしない。コピー先の `index.html` を編集し、資料固有画像を `assets/` に追加する。
ヘルパーはHTML・共通CSS・ブランド素材・検証スクリプトをコピーする。元リポジトリへの実行時依存や、採用・営業の実内容は持ち込まない。

## 設計の判断

**既定の構成を使う、部品を組み合わせる、そのページ専用に自由設計する、の3つは同格。**
CSS Grid、Flexbox、インラインSVG、画像を内容に応じて使う。特定の型、部品数、文字数に合わせて内容を削らない。
本文は1280×720pxに収め、資料固有CSSは `.deck-資料名` の中に閉じる。

- v3由来のロゴ画像、比率、位置、切り出しはキットのまま使う。描き直しや装飾としての変形をしない。
- 本文は白・ダーク・グレーを基本にし、同列の項目は同じ見た目にする。中央・最後の箱、製品のキーワード、比較の変更後という理由だけで色や太枠を足さない。
- 強調は「何の違い・状態・判断を伝えるか」を説明できる場合に使う。外しても読み取りが変わらない塗り・帯・枠・太字は外す。淡い色やグレー、黒ベタも対象。強調を毎ページ入れる必要はなく、構造は見出し・配置・余白で伝える。実際の状態や図の系列、元画像の意味ある色は保つ。
- 図を読める大きさで置き、説明との位置関係を作る。下が大きく空く場合は図の大きさや本文の組み方を見直し、空の箱を伸ばして埋めない。
- 文字と箱だけのページを続けない。元資料の図・画面の切り出し、スクショ、ロゴ、イラストの探し方と作り方は [素材の作り方](references/visual-assets.md) にある。
- 文章はキット直下の `rules/document-tone-rules.md` を参照する（このスキルの実体から4階層上）。
- 現HTML方式の基準本文級数は15px。旧方式の9pt、Arial限定、Grid禁止、40字のlead契約、150字上限等は現キットの契約ではない。

## 検証と納品

作成先で初回のみ依存とブラウザを用意し、描画を確認する。

```bash
npm ci
npx playwright install chromium
npm run check
```

作成先の検証は `index.html` が対象。`review/report.json`、各ページの `review/shots/`、`review/pdf/` が出る。
検証が通っただけで完成とはせず、各ページの画像を見て、図の欠落・写真の切れ方・不自然な余白を確認する。
強調は全ページを通して確認し、同列の要素に理由のない見た目の差があれば揃える。色を薄くするだけで済ませず、その強調が必要かを判断する。
元資料を移した場合は元ページと並べ、本文と図版の両方を照合する。

キットの共通CSS・ブランド素材（`templates/html/core/`・`assets/brand/`）は変更しない。資料固有の見た目は各資料のCSSで作る。

納品時は編集するHTMLの場所と閲覧用リンク、PDFを作った場合はその場所を伝える。
修正はそのHTMLと資料固有CSSへ反映して再描画する。HTMLキットを旧 `pineal-validate` のDOM契約で判定しない。
